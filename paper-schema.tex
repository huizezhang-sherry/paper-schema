\subsection{A schema for describing data
analysis}\label{a-schema-for-describing-data-analysis}

We represent a data analysis,
\(\mathcal{S} = \{A_1, A_2, \cdots, A_n\}\), as a sequence of \(n\)
analytical step, \(A_i\), applied to a dataset \(\mathcal{D}\), where
each step \(A_i\) is defined as

\begin{equation}
A_{i} = \langle f_{i}, \pi_{i}, r_{i}, \mathcal{I}_{i}, \mathcal{O}_{i}, \omega_{i} \rangle.
\end{equation}

The components of \(A_i\) are partitioned into a required triplet
\((f_{i}, \pi_{i}, r_{i})\) and a set of optional parameters
\((\mathcal{I}_{i}, \mathcal{O}_{i}, \omega_{i})\).
\(f_{i} \in \mathcal{F}\) denotes the methodological fork that defines
the \textbf{objective} of the analytical step (e.g.~\(f_{i}\) could be
``handle missing data'' {[}TODO: more examples{]}). Each fork is an open
question that invites multiple justifiable approaches, rather than a
closed decision that has already been resolved. The second component of
the tuple, \(\pi_{i} \in \Pi\), represents the analytical
\textbf{decision} made to resolve the fork \(f_{i}\), where \(i\)
indexes the specific choice among a set of justifiable alternatives
\(\Pi\). For example, if \(f_{i}\) is ``handle missing data'', then
\(\pi_{i}\) could be ``listwise deletion'', ``multiple imputation'', or
``model-based approach''. The term \(r_{i}\) is the epistemic or
theoretical \textbf{justification} provided for selecting path
\(\pi_{i}\). This field bridges the gap between raw code and scientific
intent, ensuring that the justification of the analysis is preserved
alongside the decision.

The operational flow of the analysis is governed by the input and output
spaces, \(\mathcal{I}_{i}\) and \(\mathcal{O}_{i}\). To maintain
computational integrity, the analysis must satisfy a sequential
consistency constraint: the inputs for any given step must be grounded
in the existing data state, comprising the original dataset and all
prior transformations. Formally, we require:

\[\mathcal{I}_{i} \subseteq \left( \mathcal{D} \cup \bigcup_{j < i} \mathcal{O}_{j} \right), \quad \forall i \in \{2, \dots, n\}\]

When the schema is extracted by Large Language Models (LLMs), we
introduce a confidence score, \(\omega_{i}\) (low, medium, high), that
can be used to trigger a clarification question when the confidence is
low. The confidence score can be particularly useful in cases where the
source text is ambiguous, guiding the LLM to seek additional information
or clarification to improve the accuracy of the schema extraction.

\subsection{Describing alternatives}\label{describing-alternatives}

A single analysis \(\mathcal{S}\) represents one realized path in the
decision space. In data analysis, there are often multiple plausible
paths that can be taken to address the same research question, each with
its own set of assumptions and implications.

For each step \(i\) in the sequence, to fulfill each fork \(f_i\), there
could be \(k_i\) decision choices to choose from:
\(\{ A_{i}^{1}, A_{i}^{2}, \dots, A_{i}^{k_i} \}\)

To identify a specific path through the multiverse, we define a
selection vector \(r = (r_1, r_2, \dots, r_n)\), where
\(r_i \in \{1, \dots, k_i\}\). A single realized analysis sequence,
\(\mathcal{S}^{r}\), is then the ordered sequence:
\[\mathcal{S}^{r} = \{ A_{1}^{r_1}, A_{2}^{r_2}, \dots, A_{n}^{r_n} \}\]

A multiverse is defined as the Cartesian product of these sets:

\[\mathcal{M} = \{ \mathcal{S}^r \mid r_i \in {1, \dots, k_i}, \forall i \}\]

The cardinality of this space, \(|\mathcal{M}| = \prod_{i=1}^n k_i\),
quantifies the total number of unique, fully-specified analysis.

\section{Application: many-analysts football
study}\label{application-many-analysts-football-study}

The many-analysts study posits fixed research questions on a fixed
dataset and invites teams of researchers to analyze the problem with
whatever software they're comfortable with. In \citet{silberzahn2018},
one question is to answer whether soccer referees are more likely to
give red cards to dark-skin-toned player than to light-skin-toned
players. The provided dataset contains two raters' rating to the picture
of players, the number of redcard received for each player/referee dyade
out of the number of games, and a collection of player, referee, and
game characteristics: player birthday, height, weight, player position,
league country, number of victories, ties, and defeats, and number of
yellow and red cards received. Most groups take a modelling approach to
estimate the effect of skin rating on the red card issued with varied
distribution assumptions (linear, logistic, and poisson) and covariate
choices as fixed and random effects. The study is comprised of an
initial analysis conducted separately by each team, followed by a
round-robin peer evaluation round, and then each group presents their
final analysis after incorporating the feedback from the discussion and
presents the results in a way they would in a published article with
formal Method section. All the materials related to the study is
publicly available on the Open Science Framework (OSF).

From the report presented by each team, we can use LLM to convert the
decisions into the schema designed and generate the corresponding coding
script. From the write-up reports, we extract the sentences relevant to
the decisions made in the final analysis by the team. This step is
needed because the original skin rating is 1-5 but later changed to 0-1
and also many teams report their initial analysis and how their final
analysis modify on top of the initial analysis. We do this to avoid
confusion on reading comprehension with LLM. For general methodology
write-up, this step is not necessarily needed {[}TODO: write it
better{]}.

We send the text description of the extractetd decisions for LLM to
generate the schema and the code script for each analysis. The code
script is run by a separate LLM to validate for potential syntax errors.
We manually in-place replace the \texttt{glm()} command with
\texttt{fixest::feglm()} \citep{fixest} for generalized linear model and
the \texttt{lme4::glmer()} \citep{lme4} function with
\texttt{glmmTMB::glmmTMB()} \citep{glmmTMB-1} for generalized mix-effect
model to speed up the evaluation of eaach script. These two functions
are in-place replacements of the classic functions for estimating the
relevant model with implementation with multi-threading in C++
\citep{fixest} and with Template Model Builder (TMB) \citep{glmmTMB-2}
for better performance. This replacement should not affect the
estimation of the effect size. All the LLM-related simulations are
conducted with claude-opus-4.5.

In the validation phase, all team scripts were successfully executed.
Notably, 10\% of the scripts (n = 2) yielded successful results without
requiring any automated syntax corrections by the validator, whereas the
vast majority (90\%) reached completion after two or three iterations.
The most frequent correction involved resolving broken and overflow
syntax in comments.

Figure~\ref{fig-res-updated} shows the agreement of the estimated effect
size, in odd ratio, from our experiments (simulated) and the published
effect size in \citet{silberzahn2018} (published). For most teams, the
simulation successfully recovers the odd ratio reported by each analyst
team, larger variations are seen in the following teams: Team 1, 9, 15,
21, 23, and 27. Here we listed the reasons for these discrepencies upon
investigation:

\begin{itemize}
\tightlist
\item
  \textbf{Team 27}: the diffference comes from the ambiguity of the
  method description, the final approach sections says \emph{In addition
  to the independent variables specified in the initial approach
  (skin-tone rating, goals scored, games played, yellow cards, and mean
  explicit and implicit bias) a variable for player position was
  included, as well as a variable for the league of the player.} The
  author is intended to include the interaction effect of rating and
  position/ league country as other variables in the initial approach,
  but the LLM interprets it as only include the main effects. This error
  can be easily caught by comparing the reproducible script provided by
  the author.
\item
  \textbf{Team 9}: the authors mistake player country for referee
  country in the text description, but their parameter estimation table
  suggests they are using player country (countryCode - Germany: France)
  instead.
\item
  \textbf{Team 23 and 1}: the discrepency comes from the LLM fails to
  properly reshape the data from a player-referee dyad per observation
  to per game observation. The schema properly identifies this step but
  the generated code doesn't execute this step properly and create a
  silent error with the validator.
\item
  \textbf{Team 15}: the discrpency comes from the default setting for
  estimating factor variable in R (our similuation) and SPSS (original
  script). In SPSS, the factor variables are estimated with effect
  coding, where the coefficients are compared to the grand mean, rather
  than to the reference group (dummy coding) in R. After changing the
  \texttt{contrast} options, we obtain the reported odd ratio.
\end{itemize}

\begin{tcolorbox}[enhanced jigsaw, title=\textcolor{quarto-callout-note-color}{\faInfo}\hspace{0.5em}{Prompt: Extracting the schema from the text}, arc=.35mm, left=2mm, opacitybacktitle=0.6, leftrule=.75mm, colbacktitle=quarto-callout-note-color!10!white, titlerule=0mm, bottomrule=.15mm, coltitle=black, toprule=.15mm, bottomtitle=1mm, toptitle=1mm, breakable, colback=white, opacityback=0, colframe=quarto-callout-note-color-frame, rightrule=.15mm]

\begin{verbatim}
You are an expert methodologist and data pipeline architect. I will
provide a text describing a multiverse analysis and a summary of the
actual dataset being used.

=== YOUR TASK ===

Extract a chronological list of methodological decisions (nodes) AND
map the exact data flow (inputs/outputs) for each node
simultaneously.

=== RULES ===

1. THEORY EXTRACTION: For each node, extract:

- 'id': A unique snake_case identifier.

- 'fork': MUST be framed as an open methodological goal that invites
multiple possible approaches. It must NOT describe the final choice.

- 'path': A 'path' is strictly a POSITIVE methodological decision
that has potential theoretical alternatives, chosen to resolve the
'fork'.

- 'rationale': WHY that decision (the path) was made, extracted from
the text.

2. DATA MAPPING: Assign 'inputs' (EXACT column names from the dataset
OR outputs from previous nodes) and 'outputs' (invented snake_case
objects like 'df_clean' or 'ranef_spec').

3. ANTI-ABSTRACTION (CRITICAL): If the text lists specific variables
(e.g., 'centered rater, meanIAT'), DO NOT summarize them away. You
MUST capture those specific variables in the 'inputs' array.

4. INLINE ARRAYS: Format arrays strictly on one line: `inputs: [var1,
var2]`.

5. CONFIDENCE & CLARIFICATION: Rate your mapping confidence (HIGH,
MEDIUM, LOW). If the text abstracts a step and you cannot confidently
match it to specific dataset columns, set confidence to LOW and
autogenerate a 'clarification_question' asking the user which exact
columns to use. If HIGH, output 'null'.

6. Output ONLY valid YAML without markdown formatting.

=== REQUIRED YAML STRUCTURE EXAMPLE ===

meta: type: schema nodes: - fork: variables are in different scales
path: apply min-max scaling to each variable justification: to put
them on the same scale for combination id: step-scaling confidence:
high - fork: combine the school variables into one dimension path:
average exp sch and avg sch justification: the most intuitive way id:
step-education confidence: low

=== DATASET SUMMARY ===

NA

=== METHODOLOGY TEXT ===

[inset text here]
\end{verbatim}

\end{tcolorbox}

\begin{tcolorbox}[enhanced jigsaw, title=\textcolor{quarto-callout-note-color}{\faInfo}\hspace{0.5em}{Prompt: generating code from the schema}, arc=.35mm, left=2mm, opacitybacktitle=0.6, leftrule=.75mm, colbacktitle=quarto-callout-note-color!10!white, titlerule=0mm, bottomrule=.15mm, coltitle=black, toprule=.15mm, bottomtitle=1mm, toptitle=1mm, breakable, colback=white, opacityback=0, colframe=quarto-callout-note-color-frame, rightrule=.15mm]

\begin{tcolorbox}[enhanced jigsaw, title=\textcolor{quarto-callout-note-color}{\faInfo}\hspace{0.5em}{Prompt: validating the code generated}, arc=.35mm, left=2mm, opacitybacktitle=0.6, leftrule=.75mm, colbacktitle=quarto-callout-note-color!10!white, titlerule=0mm, bottomrule=.15mm, coltitle=black, toprule=.15mm, bottomtitle=1mm, toptitle=1mm, breakable, colback=white, opacityback=0, colframe=quarto-callout-note-color-frame, rightrule=.15mm]

\begin{verbatim}
You are an expert R developer and automated debugging agent. The user
has provided a data file located at the relative path: `data/[insert

CRITICAL INSTRUCTIONS: 1. Fix the bug while preserving the original
intent and logic of the script.  2. If the error is a missing

STRICT OUTPUT CONSTRAINTS: - You must output ONLY valid, fully
executable R code.  - Absolutely NO markdown formatting. Do NOT wrap
your response in ```R or ```.  - Absolutely NO conversational filler,
greetings, explanations, or comments about what you fixed.  - The
first character of your response must be R code, and the last
character must be R code.
\end{verbatim}

\end{tcolorbox}

\begin{tcolorbox}[enhanced jigsaw, title=\textcolor{quarto-callout-note-color}{\faInfo}\hspace{0.5em}{Prompt: generating alternatives for a specific step}, arc=.35mm, left=2mm, opacitybacktitle=0.6, leftrule=.75mm, colbacktitle=quarto-callout-note-color!10!white, titlerule=0mm, bottomrule=.15mm, coltitle=black, toprule=.15mm, bottomtitle=1mm, toptitle=1mm, breakable, colback=white, opacityback=0, colframe=quarto-callout-note-color-frame, rightrule=.15mm]

\begin{verbatim}
You are an expert Data Analyst and Methodologist. You are reviewing
an analysis schema to identify "Forking Paths" -- alternative
analytical choices that are equally valid but distinct from the
current approach.

=== DEFINITIONS ===

The schema provided to you consists of steps with:

- **ACTION**: The goal of the step (What needs to be done).

- **DECISION**: The specific implementation chosen (How it is done).

- **JUSTIFICATION**: The reasoning behind that decision.

- **ID**: The unique identifier for the step (kebab-case).

=== TASK ===

Focus specifically on the step tagged: "[inset step number here]".
Your goal is to generate 3 distinct, valid alternatives for this
step.

For each alternative: 1. **Keep the same ACTION** (the goal remains
constant).

2. **Change the DECISION** to a different but methodologically sound
approach.

3. **Provide a new JUSTIFICATION** explaining why this alternative is
valid.

4. **Create a new ID** that reflects the new decision (must be
kebab-case).

=== OUTPUT FORMAT ===

Please output the result in **strictly valid YML format**.

**Crucial Formatting Rules:**

1. Include a `meta` section at the top with `type: alternative` and
the `step`.

2. Output strictly valid YML. All text values (decision,
justification) must be enclosed in double quotes ("). Do not use
block styles (| or >). Do not wrap lines or insert \n characters
within the quotes; keep the text as a single continuous string.

3. Do not include markdown code fences (like ```yml) or
conversational text. Just the raw YML.

=== REQUIRED YML STRUCTURE EXAMPLE ===

meta: type: tines_alternative step: [inset step number here]
alternatives: - id: step-new-method-name action: Repeat the original
action decision: "Description of the new decision..."  justification:
"This is the reasoning for why this alternative is valid."  - id:
step-another-method ...
\end{verbatim}

\end{tcolorbox}
