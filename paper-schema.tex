\begin{abstract}
A data analysis involves a sequence of decisions, from data cleaning to
model specification, each of which can affect the reported result.
Reproducing that result is not the same as understanding the sequence of
decisions that produced it and the reasons for each: the code mixes
those decisions with implementation details, while the manuscript states
the major decisions and their rationale but scatters them across its
sections and often leaves out the minor ones. A reader may then ask how
the result would change under a different decision: the question itself
is easy to pose, but implementing it is often non-trivial in practice.
In this work, we propose a schema that represents a data analysis as a
collection of decisions in natural language, from which large language
models (LLMs) can generate and validate analysis scripts directly. This
workflow can also expand a single analysis into a full multiverse of
alternatives, specified in an alternative file, ready for comparison. We
demonstrate the proposed workflow in two applications. In the first, we
construct a schema for a published regression analysis of heaped smoking
data and show that it reproduces the reported estimates, and that a
reviewer-suggested alternative can be specified through the alternative
file and turned into code automatically. In the second, where no schema
is provided, we show how the workflow serves instead as a
reproducibility check, applied to the many-analysts football study. As
an intermediate representation between the manuscript and code scripts,
our schema gives a self-contained account of an analysis and makes it
extensible from a reader's perspective.
\end{abstract}

\section{Introduction}\label{sec-intro}

A data analysis is the product of a chain of decisions, from how the
data are cleaned to how the model is specified. Those decisions are what
a reader needs in order to comprehend an analysis, judge whether it is
reasonable, and extend it by asking how the result would change under
different choices. Standard practice in reproducible research (Peng,
2011; Wrobel et al., 2024) asks for the code and the data to be made
available, but does not extend to the decisions behind them.

The distinction arises because code and the decisions it implements
operate at different levels: code specifies precisely what a computer
should do, while a decision has a contextual interpretation that the
code itself does not capture. Consider a line such as
\texttt{dplyr::filter(df,\ x\ \textgreater{}\ 0)}, which has a precise
meaning as code: keep rows where \texttt{x} is positive. Which decision
this line encodes is not something the code can answer: it could
represent restricting the analysis to a subpopulation for which
\(x > 0\) is substantively meaningful, or excluding observations flagged
as invalid by an encoding convention where \(x \le 0\) denotes
missingness, and nothing in the \texttt{filter()} syntax indicates which
is intended. Nor does code generally carry the rationale behind a
decision, unless the author has left detailed comments. A better place
to state the decisions is in the manuscript, where decisions are
described along with their rationale. But this information is scattered
across the manuscript rather than collected in one place, with
preprocessing and modeling decisions appearing in different sections of
the manuscript. Authors may also simply leave out decisions they
consider minor, on the assumption that the code provides all the detail
a reader would need. Reconstructing the full sequence, therefore, means
searching across the paper and the code for decisions and their
rationale before a reader can begin to comprehend the analysis. Ideally,
this sequence of decisions and their rationale would live in a single
file, so a reader can follow the analysis directly rather than piecing
it together from multiple sources. This file should also be extensible,
so a reader can specify an alternative decision and easily evaluate it
to see how the result would change.

In this paper, we present a schema that records a data analysis as a
sequence of decisions, each stated with the objective it addresses and
the rationale for choosing it, together with the variables it consumes
and produces. We also demonstrate how this schema, coupled with large
language models (LLMs), can be used to generate code scripts from
natural-language descriptions in manuscripts, and explore alternative
decision choices. We present two applications. The first takes the
perspective of an author supplying a schema alongside a published
manuscript, using the GAITD regression analysis of heaped smoking data
in Yee et al. (2025). A reader can then specify an alternative file,
coupled with the original schema, to compare model performance under a
different inflation-alteration specification. The second, the
many-analysts football study, considers the opposite situation, where no
schema is supplied and the workflow serves instead as a reproducibility
test. It extracts a schema from a simplified version of each team's
report, generates and validates the corresponding code, and compares the
result against that team's published estimate. Of the six teams whose
reported estimates we do not recover, three trace to reports that do not
describe the analysis precisely enough to regenerate it, including one
whose text names a different covariate from its own results table. We
further demonstrate how the schema supports specification and
exploration of three alternative random effect structures for Team 5.

The paper is organized as follows: In Section~\ref{sec-method}, we
present our methodology, including the schema representation for
describing data analysis, the specification of the alternative file, and
the workflow for generating and validating code from the schema with
LLMs. In Section~\ref{sec-gaitd}, we construct a schema for a published
GAITD regression analysis and show how it allows a reader to evaluate an
alternative specification directly. In Section~\ref{sec-application}, we
apply the workflow as a reproducibility test to the many-analysts
football study, recovering the reported results for most teams and
discussing the failed cases. Finally, in Section~\ref{sec-discussion},
we discuss the implications of our work and potential future directions.

\section{Methodology}\label{sec-method}

\subsection{A schema for describing data analysis}\label{sec-schema}

We represent a data analysis,
\(\mathcal{S} = \{A_1, A_2, \cdots, A_n\}\), as a sequence of \(n\)
analysis decisions \(A_i\), applied to a dataset \(\mathcal{D}\), where
each step, \(A_i\), is defined as a tuple:

\begin{equation}
A_{i} = \langle f_{i}, \pi_{i}, \rho_{i}, \mathcal{I}_{i}, \mathcal{O}_{i}, \omega_{i} \rangle.
\end{equation}

\(f_{i} \in \mathcal{F}\) is the \emph{objective} of a step, identifying
the problem the \emph{decision}, \(\pi_{i} \in \Pi\), is trying to
solve. \(\rho_{i}\) is the \emph{rationale} provided for choosing the
decision \(\pi_{i}\). All three fields are written in short natural
language sentences, and together they form a self-contained account of
each decision in the analysis. As an example, Listing~\ref{lst-schema}
presents the schema that describes the steps for calculating the Human
Development Index (HDI) (United Nations Development Programme, 2025):

\begin{enumerate}
\def\labelenumi{\arabic{enumi})}
\tightlist
\item
  Scale all four variables (life expectancy, expected years of
  schooling, mean years of schooling, and GNI per capita) to the {[}0,
  1{]} range.
\item
  Combine the two education variables (expected years of schooling and
  mean years of schooling) into a single education variable.
\item
  Combine the three dimensions (health, education, and income) into a
  single index using a geometric mean.
\end{enumerate}

In the file, the \texttt{meta} field at the top marks the document as a
schema (\texttt{type:\ schema}), and \texttt{nodes} below it records the
analysis as a list of steps. Each step carries an \texttt{id} that names
it, together with the \texttt{objective}, \texttt{decision}, and
\texttt{rationale} fields holding \(f_i\), \(\pi_i\), and \(\rho_i\).
For instance, the objective of step 3 is to combine the three dimensions
to create a single index. The geometric mean (the decision) is chosen
over a simple arithmetic mean (an alternative, introduced in
Section~\ref{sec-alternative}) because it penalizes uneven development
among the three dimensions (the rationale).

Generating code from the schema also requires each step to be tied to
concrete variables in the data. Where a dataset \(\mathcal{D}\) is
available, \(\mathcal{I}_i\) and \(\mathcal{O}_i\) record that mapping
as part of the schema, so that it is fixed in advance rather than
inferred at the point of code generation. Because the schema specifies
an analysis before its code exists, \(\mathcal{O}_i\) may name a
variable that is not yet in the dataset. In contrast, \(\mathcal{I}_i\)
must already be in scope, comprising variables in the original dataset
together with the outputs of all previous steps:

\[\mathcal{I}_{i} \subseteq \left( \mathcal{D} \cup \bigcup_{j < i} \mathcal{O}_{j} \right), \quad \forall i \in \{2, \dots, n\}.\]

A schema can be written by hand, or drafted by an LLM from an existing
description of the analysis, such as the methodology section of a
manuscript. In the latter case, \(\mathcal{I}_i\) and \(\mathcal{O}_i\)
are inferred by the model whenever a dataset is provided, and each step
carries a categorical confidence score, \(\omega_{i}\) (low, medium,
high), defined as the model's confidence that the recorded
\((f_i, \pi_i, \rho_i)\) correctly reflects the source text.

\subsection{Describing alternatives}\label{sec-alternative}

Recording a step's decision \(\pi_i\) does not mean it is the only one
that could satisfy its objective \(f_i\): a reader may want to revisit
the decision made for some of these steps and consider alternatives that
address the same objective, the premise of multiverse analysis
(Simonsohn et al., 2020; Steegen et al., 2016). Formally, a step in the
schema can have a candidate set of alternatives: step \(i\) may admit
\(k_i\) decisions that all satisfy its objective \(f_i\),
\(\{A_i^1, \dots, A_i^{k_i}\}\), of which the decision \(\pi_i\)
recorded in the schema is just one member, \(A_i^1\). An alternative
file specifies the remaining candidates, \(A_i^2, \dots, A_i^{k_i}\),
for a subset of steps \(C \subseteq \{1, \dots, n\}\).

The overall structure of an alternative file is shown in
Listing~\ref{lst-alternatives-skeleton}. The \texttt{meta} field at the
top identifies the file as an alternative specification
(\texttt{type:\ alternatives}), and the file-level \texttt{branch}
field, either \texttt{single} or \texttt{multi}, determines how the
candidates at each step are combined. The \texttt{nodes} field then
holds one entry for every step in \(C\). Each entry uses
\texttt{overrides} to name the step it applies to in the original
schema, then lists that step's alternative decisions and their
rationale.

Existing multiverse tooling, such as the \texttt{multiverse} package in
R (Sarma et al., 2023), expresses each branch in code, while our
alternatives are instead specified at the level of decisions, in natural
language, from which modern LLMs can generate the corresponding code.
Keeping them in a separate file also changes who can pose the
alternative question: a multiverse is conventionally built by the
original analyst exploring their own garden of forking paths, whereas an
alternative file can be written by a reader after reading the published
manuscript, against a schema the author has already supplied, to
investigate questions that interest them.

\subsection{Workflow}\label{sec-workflow}

The reliability of the generated code depends primarily on the quality
of the schema. A schema that faithfully records the decisions of an
analysis, in the form set out in Section~\ref{sec-schema}, leaves little
to be interpreted at the code generation stage, since the objective and
the decision at each step are stated explicitly. The errors that remain
are in the code implementation rather than the analysis: a missing
\texttt{library()} call, or a misnamed function argument.

The validation stage is designed to resolve errors of this kind. The
validation agent executes the script in a sandbox environment and, when
execution fails, receives the script together with the error message and
the line number at which it occurred, and returns a revised script. The
revised script is then executed again, and the cycle continues until the
script completes without error, a maximum number of attempts is reached,
or the user terminates the process. Application to the many-analysts
football study in Section~\ref{sec-application} shows that this
procedure resolves most of the syntax errors that arise in data
wrangling and statistical modeling.

The same generation-validation procedure applies to multiple analyses.
When a schema is augmented with an alternative file, the expansion
described in Section~\ref{sec-alternative} produces one schema for each
combination of decisions, and each resulting schema is passed through
the same generation and validation procedure independently.

Figure~\ref{fig-workflow} gives an overview of the workflow, which
provides two paths for using a schema. Passing a schema through the code
generation and validation stages produces a script whose execution
yields the estimates of the analysis, which can be compared with the
estimates originally reported, serving as a reproducibility check. A
schema can also be augmented with an alternative file, expanding it into
a multiverse of parallel analyses, so that the author and subsequent
readers can explore the reported result under different decisions.

\section{Application: GAITD regression of heaped smoking
data}\label{sec-gaitd}

In this section we demonstrate the workflow in the case where an author
provides a faithful schema alongside a published manuscript, which a
reader can then use to question and explore the analysis, following the
second path in Figure~\ref{fig-workflow}. We use Yee et al. (2025)'s
GAITD regression analysis of heaped smoking data, published in the
Annals of Applied Statistics, as the example. Yee et al. (2025) report
four separate smoking-related responses, and for demonstration purposes,
we build the schema for only the first response, smoking initiation age
(P1, Section 5.1 of their paper). The same workflow extends to the other
three cases.

The schema in Listing~\ref{lst-heaping} comprises fourteen entries, each
recording an \emph{objective}, a \emph{decision}, and a \emph{rationale}
in the structure introduced in Section~\ref{sec-schema}. Consider
\texttt{special\_value\_mid\_risk}: the decision is to treat ages 12-14
and 19-21 as one inflated group with extra probability mass, since these
ages show a moderate, secondary peak in the spikeplots with the
high-risk group (ages 15-18) showing the most prominent peak. Recording
the rationale along with the decision allows a reader to agree or
disagree with the authors' choice, and to question and explore the
analysis, as we do later in this section.

an alternative file, overriding three steps at once:

12-14, \texttt{alteration\_operator\_decision} turns on an alteration

\section{Application: many-analysts football
study}\label{sec-application}

Section~\ref{sec-gaitd} assumed the authors supply a schema alongside
the manuscript, but a schema need not come from the authors. Since it
records decisions in natural language, the schema can be extracted from
the manuscript itself by an LLM for readers to understand and explore
the analysis. In this section, we demonstrate the workflow in the
opposite situation, where no schema is supplied and the workflow serves
as a reproducibility test using the many-analysts football study
(Silberzahn et al., 2018).

Silberzahn et al. (2018) invited 29 research groups to conduct the same
data analysis, answering whether referees are more likely to give red
cards to dark-skin-toned players than to light-skin-toned players. The
provided dataset contains two raters' skin color ratings of players'
pictures, the aggregated number of red cards received by a player from a
referee across all matches in that player-referee pair, and other
relevant player, referee, and game characteristics: player birthday,
height, weight, player position, league country, number of victories,
ties, and defeats.

Each team was free to choose their own analysis approach; we take Team 5
as an illustration. They disaggregated the player-referee records into
player--game observations, giving a binary response for whether a player
received a red card, and removed incomplete cases by list-wise deletion.
They then fitted a binomial generalized linear mixed model with a logit
link, taking the average of the two raters' skin color ratings as the
covariate of interest, with random intercepts for players and referees
and a random intercept and slope for the referee's country of origin.

Team 5's analysis is only one of the approaches taken: other teams made
different preprocessing decisions, assumed different distributions
(linear, logistic, or Poisson), specified different fixed and random
effects, or worked in a Bayesian framework. Each team was required to
document its analysis in a report with a publishable methodology
section. All of these are available on the Open Science Framework.

These reports are not directly usable as input since the many-analysts
study also takes in a second research question and the construction of
confidence intervals. Some teams write their final analysis as a set of
edits to the initial one rather than as a self-contained methodology
section. We therefore pre-extract a simplified methodology text for each
team and use it in place of the report.

Each team's text is then passed through the workflow of
Section~\ref{sec-method} to extract the schema and then generate and
validate the corresponding code with Claude Opus 4.5. The Appendix
follows Team 5 through the pipeline to show the input text, the schema,
and the generated script.

To accelerate the evaluation of each script, we manually replace the
standard modeling functions with faster counterparts after the scripts
are generated but before validation: \texttt{lm()}/\texttt{glm()} with
\texttt{fixest::feols()}/\texttt{fixest::feglm()} (Bergé et al., 2026),
and \texttt{lme4::glmer()} (Bates et al., 2015) with
\texttt{glmmTMB::glmmTMB()} (Brooks et al., 2017). These fit the same
models by faster means, using multi-threaded C++ and Template Model
Builder (TMB) respectively, so the substitution changes how the
coefficients are computed, not the coefficients themselves.

Of the 29 teams, the analyses of four teams (Teams 7, 12, 17, and 18)
are too computationally expensive to run inside an iterative
validate-and-repair loop, regardless of whether the schema or generated
code is correct: Team 7 specifies a Dirichlet process profile
regression, Team 12 a zero-inflated Poisson regression, and Teams 17 and
18 MCMC-based hierarchical models. Hence we exclude these four teams
from the evaluation, leaving 25 teams whose analyses we attempt to
reproduce. Across the 25 teams we reproduce, all team scripts were
successfully executed after the validation phase. Notably, two scripts
ran successfully without any validation, whereas the vast majority
reached completion after two or three iterations. The most frequent
correction involved resolving broken and overflowing syntax in comments.

Figure~\ref{fig-res-schema} shows the comparison of the estimated effect
sizes, in odds ratio, from our schema workflow (reproduced) and those
reported in Silberzahn et al. (2018) (reported). The odds ratio is well
recovered for most teams, though six show a noticeably larger gap: Teams
1, 9, 15, 21, 23, and 27.

For Teams 1 and 23 the discrepancy originates in our code generation.
When reshaping the data from the player-referee level to the game level,
the schema correctly specifies this step, but the generated code fails
to execute it as intended, and the resulting error passes through
validation silently rather than triggering a repair.

For the remaining four the reported result could not be regenerated from
the report, though one of them resists diagnosis: for Team 21, examining
both the extracted schema and the generated code turned up nothing that
accounts for the gap. The other three reveal reproducibility issues in
the reports themselves. Team 9's text names ``referee country'' as the
covariate while the full report shows ``player country'' is used
instead. For Team 27, the authors write that ``a variable for player
position was included, as well as a variable for the league of the
player'', which read literally adds only main effects but might equally
be shorthand for interactions, consistent with how the other covariates
entered their initial model. Team 15 is subtler: their log-linear model
includes a skin-tone by league interaction, so the coefficient of
interest is defined relative to a parameterization the report does not
state, with SPSS's effect coding averaging it across leagues and R's
default dummy coding fixing it at a reference league. Setting
\texttt{contrasts} in R to match recovers the reported value exactly.
Neither coding is wrong, but the reported number cannot be regenerated
without knowing which one produced it. In all three cases the schema
faithfully records what's in the text, and the discrepancy that follows
points to a report whose description of the analysis is not precise
enough to regenerate the result.

Team 5 arrives at its final model by comparing three random effect
structures, a set of alternative decisions within a single modeling step
of the kind described in Section~\ref{sec-alternative}. Write
\(y_{ijm}\) for whether player \(i\) received a red card from referee
\(j\) in game \(m\), \(x_i\) for player \(i\)'s skin color rating
averaged over the two raters and rescaled to \([0, 1]\), and \(c(j)\)
for the country of origin of referee \(j\). In each model
\(y_{ijm} \sim \mathrm{Bernoulli}(p_{ijm})\), and the three differ only
in their random effects:

\[
\begin{aligned}
\textbf{gm1:} \quad \mathrm{logit}(p_{ijm}) &= \beta_0 + \beta_1 x_i + u_i + v_j, \\
\textbf{gm2:} \quad \mathrm{logit}(p_{ijm}) &= \beta_0 + \beta_1 x_i + u_i + v_{0j} + v_{1j}\, x_i, \\
\textbf{gm3:} \quad \mathrm{logit}(p_{ijm}) &= \beta_0 + \beta_1 x_i + u_i + v_j + w_{0,c(j)} + w_{1,c(j)}\, x_i,
\end{aligned}
\]

with \(u_i \sim N(0, \sigma^2_{\text{player}})\) throughout,
\(v_j \sim N(0, \sigma^2_{\text{ref}})\) in gm1 and gm3,
\((v_{0j}, v_{1j})^{\top} \sim N(\mathbf{0}, \boldsymbol{\Sigma}_{\text{ref}})\)
in gm2, and
\((w_{0c}, w_{1c})^{\top} \sim N(\mathbf{0}, \boldsymbol{\Sigma}_{\text{country}})\)
in gm3. Model gm1 lets the baseline log-odds vary across players and
referees, gm2 additionally lets the effect of skin color vary across
referees, and gm3, the model Team 5 report, instead lets both the
baseline and that effect vary across referees' countries of origin.

All three are specified in a single YAML file, following the format
described in Section~\ref{sec-alternative} and shown in
Listing~\ref{lst-yaml-alternative}. Merging it with Team 5's schema
produces one schema per alternative, and each is passed through the same
code generation and validation used for the original, yielding three
validated scripts from one file and no hand-editing of the team's code.
The estimated effect of skin tone is unchanged across this expansion,
matching the value Team 5 report and shown for this team in
Figure~\ref{fig-res-schema}.

\section{Discussion}\label{sec-discussion}

Existing reproducible practices focus on whether published results can
be reproduced from the code and data, not on the chain of decisions that
produced them. We propose a schema that records those decisions along
with the rationale for choosing them in natural language as an
intermediate representation between the manuscript and the code. A
schema can be written by an author or extracted from the manuscript by
an LLM. It can then be turned into an executable script, or expanded
into a multiverse of alternative analyses. For a published GAITD
regression, where the schema was assembled from the manuscript and its
supplement, the resulting script reproduced the reported estimates and
brought a reviewer's alternative specification within reach of any
reader. For the many-analysts football study, where no schema was
supplied, extraction and generation recovered most teams' reported
effects and identified the few where the methodology could have been
described more precisely, inconsistencies that re-running the authors'
own code would not reveal.

A data analysis question admits more than one defensible answer, and the
schema records which one was taken. Arriving at those decisions is a
matter of human judgement, whether the analyst writes the schema
directly or it is extracted from a manuscript in which the decisions
were already made. Once they are determined, generating the code is a
comparatively mechanical translation, which current LLMs perform with
reasonable reliability inside a generation-and-validation loop. Our
approach therefore contrasts with fully automated systems that use
multiple LLM agents to plan, generate, and execute analyses (Hu et al.,
2024; Jansen et al., 2025; Sun et al., 2026), which aim to automate the
decisions themselves. Donoho (2026) describes the risk in such systems
as one of premature autonomy, where the model projects an intent onto
the user rather than responding to what was asked. We do not attempt to
automate the human judgement that goes into making those decisions, but
instead provide a structured way to record them and a workflow to turn
them into code.

Three sources of uncertainty enter this pipeline, and they behave
differently as models improve. The first is implementation, where the
schema states a decision unambiguously and the generated code fails to
carry it out: the scripts for Teams 1 and 23 ran and returned estimates
after reshaping the data incorrectly. The second is extraction, where
the text states a decision clearly to a trained reader and the model
fails to recover it. In Team 5's report, the phrase ``a random effect of
skin tone across referees' countries'' is read by most statisticians as
implying both a random intercept and a slope, while read literally it
specifies only a slope, and the extraction took the literal reading
rather than the conventional one. Both are epistemic (Hüllermeier \&
Waegeman, 2021; Kendall \& Gal, 2017) and we would expect them to
diminish as models continue to improve, rather than persist as
structural limitations of the workflow. The third is aleatoric and
belongs to the source text rather than the pipeline: where a report is
ambiguous or self-contradictory, as in Teams 9, 27, and 15, no model can
recover an intent the text does not express. As extraction and
generation improve, what remains is increasingly uncertainty of this
third kind, which the schema is designed to make visible.

The validate-and-repair loop assumes that each candidate script can be
executed and diagnosed within an interactive timeframe, which rules out
analyses too expensive to run repeatedly, and Teams 7, 12, 17, and 18
were excluded on these grounds. Executing such scripts asynchronously
through a background job queue would lift the restriction without
changing the rest of the workflow.

In our pipeline the model sees the column names but never the values
themselves, for privacy reasons. Formats that the schema does not record
must therefore be learned through the validation loop. The birth dates
in the football data, used to derive player age, are a case in point:
the script for Team 21 parsed them as \texttt{\%Y-\%m-\%d} and was
corrected to \texttt{\%d.\%m.\%Y} only after one parse failure, while
the repair for Team 1 supplied four candidate formats for R to try in
turn. In both cases the date format was recovered by trial and error.
When the trials fail, the pipeline can fail outright or carry the
failure silently into the analysis.

The implementation reported here is an R package, but nothing about the
problem is specific to R, and a general-purpose tool such as a
command-line utility would support analyses written in any language. Our
implementation records the schema as a single YAML file, which gives the
decisions an explicit structure that machines can read. An alternative
is to record each decision in its own Markdown file to trade some of
that structure for flexibility in how a decision is described. Separate
files would further allow decisions to be linked over time, showing how
an analysis developed rather than only where it arrived, and with
attribution to individual researchers such a history could support a
broader research-management system.
