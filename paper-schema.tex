\begin{abstract}
Current reproducibility practices have greatly improved our ability to
replicate published results, but they do not necessarily make data
analyses easier to understand. Audience seeking to comprehend an
analysis need to piece together information scattered across manuscripts
and code scripts to understand the sequence of analytical steps and the
rationale behind them, with some details may not explicitly record in
either source. Exploring alternative analytical choices is even more
challenging, as it requires understanding and modifying code that may be
unfamiliar and consider how it would impact upstream and downstream
code. To address these challenges, we propose a schema that represents
data analyses as a collection of analytical decisions, together with
their justification, inputs, and outputs. Coupled with large language
models (LLMs), the schema can be inferred from natural language
descriptions and translated into analysis scripts. The structured
representation also enables exploration of alternative analytical
choices, allowing multiple analytical workflows to be generated and
compared. We demonstrate the proposed workflow using the many-analysts
football study, where LLMs create the schema from the decision choices
in team reports, generate corresponding analysis scripts, and explore
alternative random effect specifications. As an intermediate
representation between the manuscript and code scripts, our schema makes
analyses more comprehensible and extendable from a reader's perspective.
\end{abstract}

\section{Introduction}\label{sec-intro}

When we want to understand a published data analysis, beyond simply
being able to re-run it, there is currently nothing we can use directly
for this purpose. Code and data availability, now standard practice
following a broader push for reproducible research (Peng, 2011; Wrobel
et al., 2024), guarantee that a result can be regenerated, but they say
nothing about whether a reader can track the decisions the authors made,
understand the rationale behind them, or comfortably modify the code to
explore alternative choices.

Part of the difficulty is that code and the applied researchers who
write it operate at different levels: code specifies precisely what a
computer should do, while a researcher reasons about what decision that
computation represents in the context of their analysis, a gap also
identified in prior work on authoring statistical models from conceptual
relationships (Jun, Seo, et al., 2022; Jun, Birchfield, et al., 2022).
Consider a line such as
\texttt{dplyr::filter(df,\ x\ \textgreater{}\ 0)}, which has a precise,
unambiguous meaning as code: keep rows where \texttt{x} is positive. As
an analytical decision, however, that same line could represent
restricting the analysis to a subpopulation for which
\texttt{x\ \textgreater{}\ 0} is substantively meaningful, or excluding
observations flagged as invalid by an encoding convention where
\(x \leq 0\) denotes missingness; nothing in the \texttt{filter()}
syntax gives any indication of which of these two decisions is being
made. Tools such as \texttt{tidyverse} (Wickham et al., 2019) have
worked to align code more closely with the action being performed,
naming operations after what they do rather than how they are
implemented. But knowing the action a line of code performs is not the
same as knowing the decision it encodes: an analysis requires additional
context that the action alone does not carry.

This suggests that a more effective representation of an analysis would
be one that describes the decisions made and their rationale, allowing
readers to understand the analysis without needing to parse the code
itself or reconstruct the rationale from the manuscript. Recent advances
in Large Language Models (LLMs) for code generation make such a
representation practical: LLMs are now widely used for code generation
tasks, demonstrating strong capabilities in translating natural language
descriptions into executable programs (Chen et al., 2021; Huang et al.,
2022; Jiang et al., 2026; Lai et al., 2023; Shah et al., 2026). Once a
decision is described in a schema, an LLM can generate and validate the
corresponding code directly from it.

This same representation also makes extending an analysis easier. Data
analysis is often underdetermined, with many plausible choices regarding
data preprocessing, transformation, aggregation, and model specification
(Bertran et al., 2026; Gao \& Xiao, 2026; Luo et al., 2025), and a
reader may reasonably want to know whether a conclusion would still hold
under one of these other choices, for example, ``What if we had included
observations with \(x \leq 0\)?'' Because each decision is recorded
explicitly rather than embedded in code, a reader can specify such an
alternative directly and have it evaluated through the same schema and
the same LLM-based translation into code, rather than modifying the
original script by hand.

In this paper, we present a schema designed to describe data analysis in
a structured way that captures the decisions and their justifications,
as well as the inputs and outputs of each step. We also demonstrate how
this schema, coupled with LLMs, can be used to generate code scripts
from natural-language descriptions in manuscripts, and explore
alternative decision choices. We apply our schema to the many-analyst
football study, where LLMs create the schema from the decision choices
reported in the final reports of each team, and generate and validate
the corresponding code scripts against the original published results.
In the process, we also uncover an inconsistency in one team's published
report between the covariate described in the text and the one implied
by their results. We further demonstrate how to the schema supports
specification and exploration of alternatives random effect
specification for Team 5.

The paper is organized as follows: In Section~\ref{sec-method}, we
present our methodology, including the schema representation for
describing data analysis and the workflow for generating and validating
code from the schema by LLMs. In Section~\ref{sec-application}, we apply
our methodology to the many-analyst football and demonstrate that we can
reproduce the results reported in the paper, identify errors in the
original reports, and highlight failure modes of current LLMs. Finally,
in Section~\ref{sec-discussion}, we discuss the implications of our work
and potential future directions.

\section{Methodology}\label{sec-method}

As traditional reproducibility practices can be insufficient for
understanding complex modern data analyses, we have designed two
complementary YAML schemas and the associated workflow to better support
comprehension and extensibility in applied data analysis. Our workflow
is designed to be 1) decision-centric: analyses are represented as a
sequence of decisions with explicit rationale, and 2) reader-oriented
exploration: readers can inspect, compare, and extend those decisions.

\subsection{A schema for describing data
analysis}\label{a-schema-for-describing-data-analysis}

We represent a data analysis,
\(\mathcal{S} = \{A_1, A_2, \cdots, A_n\}\), as a sequence of \(n\)
analytical step \(A_i\), applied to a dataset \(\mathcal{D}\), where
each step, \(A_i\), is defined as a tuple:

\begin{equation}
A_{i} = \langle f_{i}, \pi_{i}, \rho_{i}, \mathcal{I}_{i}, \mathcal{O}_{i}, \omega_{i} \rangle.
\end{equation}

The components of \(A_i\) can be partitioned into two parts: a required
triplet \((f_{i}, \pi_{i}, \rho_{i})\) and an optional triplet
\((\mathcal{I}_{i}, \mathcal{O}_{i}, \omega_{i})\). The first component
of the triplet, \(f_{i} \in \mathcal{F}\) is the \emph{objective} of a
step. The second component, \(\pi_{i} \in \Pi\), represents the specific
\emph{decision} made to achieve the objective \(f_{i}\) and the term
\(\rho_{i}\) is the \emph{justification} provided for choosing the
decision \(\pi_{i}\). Structuring this information into a schema
involves defining the three components described above for each step.
While the decision (what has been done) and the justification (why it is
done) are generally clear, the objective requires identifying what the
step is trying to achieve. In other words, it represents the broader
goal that could potentially be fulfilled through other alternative
choices (formally introduced in Section~\ref{sec-alternative}). As an
example, consider the description for calculating the Human Development
Index (HDI) (United Nations Development Programme, 2025):

\begin{enumerate}
\def\labelenumi{\arabic{enumi})}
\tightlist
\item
  Scale all four variables (life expectancy, expected years of
  schooling, mean years of schooling, and GNI per capita) to the {[}0,
  1{]} range.
\item
  Combine the two education variables (expected years of schooling and
  mean years of schooling) into a single education variable.
\item
  Combine the three dimensions (health, education, and income) into a
  single index using a geometric mean.
\end{enumerate}

In Step 3, the objective is to combine the three dimensions. While a
simple arithmetic mean could be an alternative decision to fulfill this
goal, the geometric mean (the decision) is chosen because it penalizes
uneven development among the three dimensions (the justification). The
full schema for constructing HDI is presented in
Listing~\ref{lst-schema}.

\begin{codelisting}

\caption{\label{lst-schema}An example schema for calculating Human
Development Index (HDI)}

\centering{

\begin{verbatim}
meta:
  type: schema
nodes:
- tag: step-scaling
  objective: how to handle variables in different scales?
  decision: apply min-max scaling to each variable 
  rationale: to convert the variables to the same scale for future 
    construction of a single index
- tag: step-education
  objective: how to combine the two education-related variables?
  decision: take the average
  rationale: the arithmetic mean allows perfect substitutability 
    between the two variables
- tag: step-combine
  objective: how to combine the three dimensions into a single index?
  decision: use the geometric mean
  rationale: the geometric mean penalizes uneven development 
    among the three core dimensions
\end{verbatim}

}

\end{codelisting}%

On the optional components of a data analysis step \(A_i\), the
operational flow of the analysis is governed by the input and output
spaces, \(\mathcal{I}_{i}\) and \(\mathcal{O}_{i}\) respectively, once a
dataset is provided. While the output of a step can be a pseudo object
that not currently exist in the dataset, the inputs for any given step
must be within the existing data scope, comprising variables in the
original dataset and all outputs from previous steps. Formally, we
require:

\[\mathcal{I}_{i} \subseteq \left( \mathcal{D} \cup \bigcup_{j < i} \mathcal{O}_{j} \right), \quad \forall i \in \{2, \dots, n\}.\]

When the schema is extracted automatically by Large Language Models
(LLMs) from text, the inputs and outputs will be inferred by the LLMs,
if a dataset is provided. We also introduce a categorical confidence
score, \(\omega_{i}\) (low, medium, high) that can be useful in case
when the source text is ambiguous to guide the LLM to ask for
clarification to consolidate the schema extraction.

\subsection{Describing alternatives}\label{sec-alternative}

At each step, one decision choice is made by the researchers to address
an objective, however the choice is often not the only possible one. For
step \(i\), there could be \(k_i\) decision choices that fulfill the
objective \(f_i\): \(\{ A_{i}^{1}, A_{i}^{2}, \dots, A_{i}^{k_i} \}\).
We can define a selection vector \(r = (r_1, r_2, \dots, r_n)\), where
\(r_i \in \{1, \dots, k_i\}\), to describe an analysis comprised of
specific series of decisions:
\(\mathcal{S}^{r} = \{ A_{1}^{r_1}, A_{2}^{r_2}, \dots, A_{n}^{r_n} \}\).
A multiverse, used to describe the entire decision space (Simonsohn et
al., 2020; Steegen et al., 2016), is defined as the Cartesian product of
these sets:
\(\mathcal{M} = \{ \mathcal{S}^r \mid r_i \in {1, \dots, k_i}, \forall i \}\).
The cardinality of this space, \(|\mathcal{M}| = \prod_{i=1}^n k_i\),
quantifies the total number of unique, fully-specified analysis.

Returning to the HDI example, in Step 3, instead of a geometric mean, an
arithmetic mean is another possibility to combine the three dimensions
into a single index. It may not be the best decision, but still a
plausible one to derive a single index from the three dimensions, hence
achieve the objective of this step. Listing~\ref{lst-alternatives} shows
the structure of an alternative YAML file. The \texttt{meta} section
identifies the file type (an alternative file rather than a schema file)
and specifies the analysis step and the objective under consideration.
Individual alternatives are defined as entries in the alternatives list,
allowing multiple alternatives to be specified within a single file.

\begin{codelisting}

\caption{\label{lst-alternatives}An example YAML file for specifying
alternative for Step 3 in calculating Human Development Index (HDI).}

\centering{

\begin{verbatim}
meta:
  type: alternative
  step: step-combine
  objective: how to combine the three dimensions into a single index?
alternatives:
  - id: arith-mean
    decision: use an arithmetic mean
    rationale: a simple average of the three dimensions
\end{verbatim}

}

\end{codelisting}%

\subsection{Workflow}\label{workflow}

The overall workflow for schema-based data analysis is illustrated in
Figure~\ref{fig-workflow}. A schema can be created either manually from
the template or automatically by an LLM from a natural-language
manuscript. Once created, the schema serves as a structured
specification that guides a second LLM in generating the code for the
analysis. To improve reliability, our design includes a third LLM agent
which is responsible for code validation. While the latest LLMs can
generate reasonable code based on prompt, they do not consistently
achieve perfect accuracy. The validation process runs the generated
script in a sandbox environment and if an error occurs, a third LLM
agent will be employed to diagnose the script. The validation agent
receives the generated code together with the error message and the
corresponding line number produced during the execution, and returns a
newer version of the script. The revised script is then re-executed in
the sandbox and this cycle continues until one of the three conditions
is met: the code runs successfully, a maximum number of attempt is
reached, or the user terminates the process. As will be show in
Section~\ref{sec-application}, this validation process resolves the
majority of R syntax issues encountered during data wrangling and
statistical modelling tasks. On top of supporting a single analytical
specification, the workflow also allows users to argument a schema with
an alternative YAML file. This expands the original schema into a
multiverse of parallel schemas, each representing a different sequence
of decision choices. The same code generation and validation workflow is
then applied independently to each schema, producing a corresponding set
of validation scripts.

\begin{figure}

\centering{

\includegraphics[width=1\linewidth,height=\textheight,keepaspectratio]{figures/workflow.png}

}

\caption{\label{fig-workflow}Overview of the schema-driven analysis
workflow. Schemas can be authored manually or generated from natural
language manuscripts by an LLM. Schemas are used to generate code, which
is validated through iterative execution in a sandboxed environment and
repaired when errors occur. Alternative specifications can expand a
schema into a multiverse of parallel analyses.}

\end{figure}%

Returning to the HDI example, the proposed workflow allows both authors
and readers to interact with a data analysis through natural language.
The schema in Listing~\ref{lst-schema} is straightforward to construct
from a template and can be included as supplementary material to
document the analytical workflow. An author may use the ``code
generation and validation'' path in Figure~\ref{fig-workflow} to
automatically generate the analysis script for computing HDI and
validate its accuracy. A reader, on the other hand, may wish to explore
how the HDI values or country rankings change if the original arithmetic
mean (instead of the geometry mean) is used. By combining the original
schema in Listing~\ref{lst-schema} with the alternative specification
Listing~\ref{lst-alternatives}, the ``alternative generation'' path
produces a corresponding analysis script for each alternative with LLMs.
In contrast, modifying an existing code script by hand typically
requires manually coordinating changes across upstream and downstream
code. By representing analyses as a sequence of structured analytical
decisions, our workflow allows LLMs to automate much of this process,
making it easier to understand the sequence of steps taken in the
analysis and to explore alternatives.

\section{Application: many-analysts football
study}\label{sec-application}

In this section, we apply our methodology to the many-analyst football
by Silberzahn et al. (2018) to reproduce the reported estimated effect
size by each team. During this process, we identify some errors in the
original reports and highlight failure modes of current LLMs.

Silberzahn et al. (2018) invites 29 research groups to conduct the same
data analysis to answer whether are more likely to give red cards to
dark-skin-toned player than to light-skin-toned players. The provided
dataset contains two raters' skin color rating to players' picture, the
aggregated number of red card received by a player from a referee across
all matches in that player-referee pair, and other relevant player,
referee, and game characteristics: player birthday, height, weight,
player position, league country, number of victories, ties, and defeats,
and number of yellow and red cards received. In Silberzahn et al.
(2018), each group first conducted an initial analysis separately,
followed by a round-robin peer evaluation. Each group was then given the
opportunity to incorporate feedback from the discussion and submitted a
final analysis as a report with a formal Method section. All the
materials related to the study is publicly available on the Open Science
Framework (OSF).

Based on the reports presented by each team, most participating groups
adopted a modelling approach to estimate the effect of skin color rating
on the likelihood of receiving a red card. As an illustrative example,
Group 5 first transformed the data into player--game observations,
resulting in a binary response variable for whether a player received a
red card, and removed observations with missing values using list-wise
deletion. The resulting data were modelled using a generalized linear
mixed model (GLMM) with a binomial error distribution. The average skin
color rating from two raters was used as the primary covariate, and its
estimated coefficient was the main parameter of interest. To account for
unobserved heterogeneity, the model included random effects for player
and referee, as well as the average skin color rating across referee's
country of origin. While Group 5's analysis illustrates one possible
approach, other groups may adopt different data preprocessing decisions,
distributional assumptions (e.g., linear, logistic, or Poisson models),
specification of fixed and random effects, or conduct the analysis in a
Bayesian framework.

We use LLM to convert the methodology description into the schema we
propose and generate the corresponding code script. We observe that most
reports are structured to first describe the initial data analysis and
then the changes made in the final analysis. To avoid testing LLMs'
ability to reconstruct how analysis steps are modified, overturned, or
carried over from the initial to the final analysis, we extract the
descriptions relevant to the final analysis.

We send the text description of each team for LLM to generate the schema
and then generate the code script from the schema. The code script is
run by a separate LLM to validate for potential syntax errors.

To accelerate the evaluation of each script, we manually in-place
replace the \texttt{glm()} command with \texttt{fixest::feglm()} (Bergé
et al., 2026) for generalized linear model and the
\texttt{lme4::glmer()} (Bates et al., 2015) function with
\texttt{glmmTMB::glmmTMB()} (Brooks et al., 2017) for generalized
mix-effect model after the scripts are generated but before the
validation. These two functions are in-place replacements of the
standard functions for estimating the relevant model with
multi-threading in C++ (Bergé et al., 2026) and Template Model Builder
(TMB) (McGillycuddy et al., 2025) for better performance. This
replacement should not affect the estimation of the effect size. All the
LLM-related simulations are conducted with claude-opus-4.5.

Across the 25 teams we reproduce, all team scripts were successfully
executed after the validation phase. Notably, two scripts run
successfully without any validation whereas the vast majority reached
completion after two or three iterations. The most frequent correction
involved resolving broken and overflow syntax in comments.

\caption{\label{fig-res-updated}Comparison of the odd ratio of the

simulation with the schema (simulated) vs.~the reported estimated effect
size in Silberzahn et al. (2018) (published). Teams are arranged by the
difference in odd ratio of our simulation and the reported value. For

\end{figure}%

Figure~\ref{fig-res-updated} shows the comparison of the estimated
effect size, in odd ratio, from our workflow (simulated) and those
reported in Silberzahn et al. (2018) (published). The odd ratio is well
recovered for most teams, though six show a noticeably larger gap: Team
1, 9, 15, 21, 23, and 27. Looking closely at each team's report and
generated script, the causes split into two stages of our pipeline, plus
one case that has nothing to do with the LLM at all.

For Team 27, the report is genuinely ambiguous: the authors write that,
``In addition to the independent variables specified in the initial
approach, \ldots{} a variable for player position was included, as well
as a variable for the league of the player.'' A statistician reading
this might reasonably take it as shorthand for extending the model with
interactions, consistent with how the other covariates entered the
initial model, but the LLM read it literally and added only main
effects. Team 9 fails for a similar reason at the same stage: the text
names ``referee country'' as the covariate, yet the reported estimation
table lists ``player country'' instead, and the LLM followed the text
rather than reconciling it against the table. In both cases the schema
itself is already wrong before any code is written, so we treat these as
schema-extraction errors.

Team 1 and Team 23, by contrast, get the schema right but the code
wrong. Both require reshaping the data from player-referee pairs to
individual games, disaggregating win/loss/draw counts into game-level
records. The schema correctly specifies this step, but the generated
code fails to execute it as intended, and the resulting error passes
through validation silently rather than triggering a repair.

Team 15's discrepancy is unrelated to either stage: it comes down to a
difference in default contrast coding between R (our reproduction) and
SPSS (the original analysis) --- SPSS's effect coding compares each
level to the grand mean, while R's default dummy coding compares to a
reference level. Setting the \texttt{contrast} option in R to match
recovers the reported odd ratio exactly, so this reflects a software
convention rather than a modeling or LLM error.

That leaves Team 21, whose discrepancy we have not yet traced to a
specific cause {[}TODO: resolve before submission{]}. With that
exception, the pattern across the remaining five teams is that LLM error
is split evenly between the schema-extraction and code-generation
stages, while the sixth discrepancy is a reproduction artifact rather
than a model failure.

\subsection{Exploring alternatives}\label{exploring-alternatives}

During the modelling process, researchers may consider a range of
alternative specifications, such as different covariate and random
effects structures, before arriving at a final model. This can be seen
as a set of alternative decisions within the same modelling step, which
fits naturally into the schema workflow described in
Section~\ref{sec-alternative}. As an example, we use Team 5 for the
above football study to demonstrate the use case. Team 5 uses a binomial
generalized linear mixed model (GLMM) to estimate the effect of skin
tone rating on the number of red cards received using a logit link
function, but tests different random effect structures:

\begin{align*}
\textbf{Model 1 (gm1):} \quad \text{logit}(p_{ijk}) &= \beta_0 + \beta_1 X_{ijk} + u_{j} + v_{k} \\
u_{j} &\sim N(0, \sigma^2_{\text{player}}), \quad v_{k} \sim N(0, \sigma^2_{\text{ref}}) \\[1.5em]
\textbf{Model 2 (gm2):} \quad \text{logit}(p_{ijk}) &= \beta_0 + \beta_1 X_{ijk} + u_{j} + v_{0k} + v_{1k} X_{ijk} \\
u_{j} &\sim N(0, \sigma^2_{\text{player}}), \quad \mathbf{v}_{k} \sim N\left(\mathbf{0}, \boldsymbol{\Sigma}_{\text{ref}}\right) \\[1.5em]
\textbf{Model 3 (gm3):} \quad \text{logit}(p_{ijkm}) &= \beta_0 + \beta_1 X_{ijkm} + u_{j} + v_{k} + w_{0m} + w_{1m} X_{ijkm} \\
u_{j} &\sim N(0, \sigma^2_{\text{player}}), \quad v_{k} \sim N(0, \sigma^2_{\text{ref}}), \quad \mathbf{w}_{m} \sim N\left(\mathbf{0}, \boldsymbol{\Sigma}_{\text{country}}\right)
\end{align*}

where \(p\) denotes the probability of a player receiving a red card,
and \(X\) represents the player's skin tone rating. The subscripts
\(i, j, k,\) and \(m\) index the individual observation, player,
referee, and the referee's home country, respectively. The parameter
\(\beta_0\) represents the global baseline log-odds of receiving a red
card, and \(\beta_1\) estimates the fixed effect of a player's skin
tone. The random effect include

\begin{itemize}
\tightlist
\item
  a random intercept for players,
  \(u_j \sim N(0, \sigma^2_{\text{player}})\), in Model 1, 2, and 3,
\item
  a random intercept for referee,
  \(v_k \sim N(0, \sigma^2_{\text{ref}})\), in Model 1 and 3, an
  additional random slope for referee in Model 2, and
\item
  a random intercept and slope for referee countries,
  \(\mathbf{w}_{m} \sim N\left(\mathbf{0}, \boldsymbol{\Sigma}_{\text{country}}\right)\),
  in Model 3.
\end{itemize}

These alternatives are specified in a separate YAML file described in
Section~\ref{sec-alternative} as Listing~\ref{lst-yaml-alternative}.
This file is then merged with the original schema to produce one
separate schema for each alternative for code generation and validation.
The validated scripts are then executed to obtain the estimated random
effects in Table~\ref{tbl-random-effects}. This result matches with the
random effects reported in the team report, subject to rounding errors.
Similarly, the model fitting statistics can be extracted from the
estimation for selecting the best fit.

\section{Discussion}\label{sec-discussion}

Our results highlight a persistent gap between computational
reproducibility and analytical understandability in modern data analysis
workflows. While current reproducibility practices ensure that published
results can be regenerated from shared data and code, as analyses grow
in complexity and involve iterative decision-making processes, they are
less of an ideal for readers to understand. Our proposed schema
addresses this gap by introducing an intermediate representation that
explicitly encodes analytical decisions to bridge between narrative
descriptions and implementation details. When coupled with LLMs, this
representation enables the extraction of analytical structure from
written reports and its translation into analysis scripts, and
supporting the exploration of alternative analytical choices.

Our approach differs in this respect from recent work that builds fully
automated systems using multiple LLM agents to plan, generate, execute,
and refine data analyses (Hu et al., 2024; Jansen et al., 2025). These
systems rely on the same underlying capability of translating analytical
specifications into code that our workflow uses, but they aim to
automate the analytical decisions themselves, not just their translation
into code. The failure modes we document in
Section~\ref{sec-application} suggest this is premature: even the
comparatively narrower task of translating an already-specified decision
into working code is not yet fully reliable. We take this as support for
our position that the harder and more consequential part of a data
analysis is the sequence of decisions a researcher makes, not the code
that implements them, and that this part should remain explicit and in
the hands of the analyst rather than be automated away.

To further examine how this workflow behaves in practice, we apply it to
the many-analysts football study. This analysis allows us to identify
errors in the original reports and to characterize failure modes of
current LLMs to generate code for data science. Beyond validating the
workflow itself, the schema-driven reanalysis catches a real
inconsistency in a published report (Team 9's text-table mismatch,
discussed in Section~\ref{sec-application}), which without an explicit
account of the underlying decisions, would not have caught through
computational reproducibility alone. Decomposing the largest
discrepancies between our reproduced and reported effect sizes reveals
that LLM error arises from two distinct stages of the pipeline, in
roughly equal measure: mis-extraction of the schema from an ambiguous
report, and correct schema extraction followed by incorrect code
generation. This distinction matters for where future effort should be
directed --- schema-extraction errors call for better disambiguation
strategies (e.g., using the confidence score \(\omega_i\) to prompt for
clarification, as introduced in Section~\ref{sec-method}), whereas
code-generation errors call for improvements to the validation stage
itself.

For the schema-extraction errors specifically, we find that LLMs require
a fairly precise specification in order to generate the code correctly
for the intended random effect structure. For an educated statistician,
the phrase ``a random effect of referee number across average rating''
would typically imply both a random intercept and a random slope.
However, we observe that LLMs interpret this specification literally as
a random slope only. This suggests the gap between the latest models and
human analysts in specialized statistical knowledge (Sun et al., 2026).

For the code-generation errors, the LLM successfully corrects a range of
implementation issues during validation, including errors caused by
overflowing comments and other syntax issues. However, we also observe
challenges in data reshaping tasks when the transformation requires
changes in the unit of analysis. In the study, some teams decide to
transform the data from the original aggregated player-referee
dyad-level format to game-level format. This transformation requires
disaggregating aggregated outcome counts (win, loss, and draw) into
individual game records, changing the unit of analysis from dyads to
matches. We also observe some difficulties in parsing birthdates. Since
the LLM does not have access to the underlying raw data, due to privacy
constraint, it must rely on trial and error when inferring the correct
date formats (``DD-MM-YYYY.''). This suggests that certain types of data
analysis tasks may not be fully automatable in settings where the model
cannot directly inspect the data, even if the data is theoretically
available for computation.

The reproducibility-understandability issue considered in this work is
still at an early stage, some software decision choices are worth
examining. We currently implement a prototype as an R package, although
the understandability problem is broadly applicable to statistical
analyses and is not associated to any particular programming language.
Hence, we envision the implementation eventually evolving into a general
purpose tool, such as a command-line utility, that can support analyses
across different programming languages. In the current implementation,
analytical decisions are recorded in a single YAML file. An alternative
would be to record individual decisions in separate Markdown files.
While YAML files provide an explicit structure for machine readability,
markdown files offer greater flexibility for documenting decisions.
Recording decisions in separate files would also allow files to be
linked across time to understand how decisions evolve or change over the
course of an analysis and can potentially support a broader
research-management system if the decisions are properly attributed to
individual researchers and maintains a record of the changes leading to
the final analysis.
