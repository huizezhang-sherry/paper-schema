1 Introduction

Reporting the sequence of steps and decisions taken in a data analysis is a crucial part of presenting evidence in publications for new scientific discoveries. Modern data analyses have grown in complexity, with data coming from multiple sources and are potential spatial, temporal, and multivariate nature. To ensure the reproducibility of reported results, good practices are advocated to make code scripts publicly available or adopt literate programming techniques. To this date, reproducibility checks by the journals have been a standard screening process in the publication pipeline in statistics.

One implicit assumption the current practices operates under is that an analysis becomes reproducible, hence understandable, once all the reproducible materials are made available. Specifically, understandable implies that an independent researcher should be able to, without much difficulty, track the steps that have been done on the data and understand why each step was taken. In practice, however, reconstructing an analysis is rarely straightfoward. Instead, it is often a frustrating cycle of trial and error, hitting failure points with little feedback on when things go wrong. Part of the reason is that the two media (manuscripts and code scripts) serve different communication goals. A manuscript is a curated narrative designed to present new scientific discoveries, rather than an algorithmic log of the data analysis workfllow. Code scripts, on the other hand, show all the computational details but don’t inherently carry the underlying scientific rationale behind each step. Additionally, code scripts reflect author’s choice of pragramming language, personal coding style, and customized abstractions built to streamline repetitive analytical tasks. These all create obstables for readers attempting to parse the code and hinder their ability to confidently modify or extend the analysis.

Hence, a gap still exists between an analysis being machine replicable and reader understandable, requiring researchers to spend a non-trivial amount of time piecing together information from the manuscript and code scripts. With recent advances in large language models (LLMs), we have the opportunity to rethink how we can present data analysis in a way that is more structured and to facilitate comprehension and exploration of alternatives. LLMs have shown remarkable capabilities in understanding human language and in generating code from natural language descriptions. This opens up new possibilities to bridge the gap from reproducibility to understandability.

In this paper, we present a schema designed to describe data analysis in a structured way that captures the key decisions and their justifications, as well as the inputs and outputs of each step. We also demonstrate how this schema can be used to generate code scripts from textual descriptions of analyses, and to explore alternative analytical paths given the power of LLMs for code generation. We apply our schema to a case study of the many-analyst football study, where we extract the analytical decisions from the final reports of each team, generate the corresponding code scripts, and validate the results against the published results in the original paper. We also demonstrate how to specify and explore alternatives for a specific step in the analysis using our schema.

The paper is organized as follows. In Section 2, we review the relevant literature on communication of data analysis and reproducibility, as well as agentic data science. In Section 3, we present our methodology, including the schema for describing data analysis and the process for generating and validating code from the schema by LLMs. In Section 4, we apply our methodology to the many-analyst football study and present our results. Finally, in Section 5, we discuss the implications of our work and potential future directions.

3 Methodology

3.1 A schema for describing data analysis

We represent a data analysis, \(\mathcal{S} = \{A_1, A_2, \cdots, A_n\}\), as a sequence of \(n\) analytical step, \(A_i\), applied to a dataset \(\mathcal{D}\), where each step \(A_i\) is defined as a tuple:

\[\begin{equation} A_{i} = \langle f_{i}, \pi_{i}, r_{i}, \mathcal{I}_{i}, \mathcal{O}_{i}, \omega_{i} \rangle. \end{equation}\]

The components of \(A_i\) are partitioned into a required triplet \((f_{i}, \pi_{i}, r_{i})\) and a set of optional components \((\mathcal{I}_{i}, \mathcal{O}_{i}, \omega_{i})\). The first component of the triplet, \(f_{i} \in \mathcal{F}\), defines the objective of a data analysis step that invites multiple justifiable approaches. The second component, \(\pi_{i} \in \Pi\), represents the data analysis decision made to achieve the objective \(f_{i}\), which can be read from both the manuscript and from the code script. The term \(r_{i}\) is the justification provided for choosing the decision \(\pi_{i}\). This field is usually provided in the manuscript but not the code script to show the scientific intent of the step. As an example, consider the three steps involved in calculating the Human Development Index (HDI):

  1. Scale all four variables (life expectancy, expected years of schooling, mean years of schooling, and GNI per capita) to a [0, 1] range using their corresponding upper and lower limits.
  2. Combine the two education-related variables (expected years of schooling and mean years of schooling) into a single education variable.
  3. Combine the three core dimensions (health, education, and income) into a single index using a geometric mean.

Structuring this information into a schema is involves defining the objective, decision, and justification for each step. While the decision (what is to be done) and the justification (why it is done) are generally clear, the objective requires identifying what the step is trying to achieve. In other words, it represents the broader goal that could potentially be met through alternative methods (formally introduced in Section 3.2 ). For instance, in step 3, the objective is to combine the three dimensions. While a simple arithmetic mean could be an alternative solution for this goal, the geometric mean is specifically chosen because it penalizes uneven development among the three dimensions—this reasoning forms the justification. On the optional components of a data analysis step \(A_i\), the operational flow of the analysis is governed by the input and output spaces, \(\mathcal{I}_{i}\) and \(\mathcal{O}_{i}\), once a dataset is provided. While the output of a step can be a pseudo object that not currently exist, the inputs for any given step must be within the existing data scope, comprising variables in the original dataset and all outputs from previous steps. Formally, we require:

\[\mathcal{I}_{i} \subseteq \left( \mathcal{D} \cup \bigcup_{j < i} \mathcal{O}_{j} \right), \quad \forall i \in \{2, \dots, n\}.\]

A schema can also be automatically extracted by Large Language Models (LLMs) from text. If a dataset is provided, the inputs and outputs will also automatically inferred during the extraction. We also introduce a categorical confidence score, \(\omega_{i}\) (low, medium, high) that can be useful in case when the source text is ambiguous to guide the LLM to ask for clarification to consolidate the schema extraction.

3.2 Describing alternatives

While one analysis represents a realized series of choices, alternatives can often be taken for to address the same objective, each with its own set of assumptions and implications. For each step \(i\) in the sequence, to fulfill each fork \(f_i\), there could be \(k_i\) decision choices to choose from: \(\{ A_{i}^{1}, A_{i}^{2}, \dots, A_{i}^{k_i} \}\). We can define a selection vector \(r = (r_1, r_2, \dots, r_n)\), where \(r_i \in \{1, \dots, k_i\}\), to describe an analysis, comprised of specific series of decisions: \(\mathcal{S}^{r} = \{ A_{1}^{r_1}, A_{2}^{r_2}, \dots, A_{n}^{r_n} \}\). A multiverse, used to describe the entire decision spae, is defined as the Cartesian product of these sets: \(\mathcal{M} = \{ \mathcal{S}^r \mid r_i \in {1, \dots, k_i}, \forall i \}\). The cardinality of this space, \(|\mathcal{M}| = \prod_{i=1}^n k_i\), quantifies the total number of unique, fully-specified analysis.

Returning to the HDI example, in step 3, instead of a geometric mean, an arithmetic mean to combine the three dimensions into a single index. It may not be the best decisions, but still a plausible one to achieve the objective of this step. Listing 2 demonstrates how this single alternative is structured in an alternative YAML file. Additional alternatives can be specified by adding items to the alternatives list.

3.3 Workflow

The overall workflow for schema-based data analysis is illustrated in Figure 1. A schema can be created either manually from a template or automatically generated by an LLM from a natural-language manuscript. Once created, the schema serves as a structured specification that guides a second LLM in generating the code for the analysis. To improve reliability, our design include a third LLM agent responsible for code validation. While recent LLMs can generate reasonable code based on prompt, they do not consistently achieve perfect accuracy. The validation process runs the generated script in a sandbox environment and if an error occurs, the third LLM agent is invoked to diagnose the script. The validation agent receives the generated code together with the error message adn teh correponding line number produced during execution, and returns a fixed version of the script. The revised script is then re-executed in the sandbox. This cycle continues until the code runs successfully, a maximum number of attempt is reached, or the user terminates the process. As will be show in Section 4, this validation process resolves the majority of R syntax issues encountered during data wrangling and statistical modelling tasks. On top of supporting a single analytical specification, the workflow also allows users to agument a schema with an alternative YAML file. This expands the original schema into a multiverse of parallel schemas, each representing a different set of decision choices. The same code generation and validation workflow is then applied independently to each schema, producing a corresponding set of validation scripts.

4 Application: many-analysts football study

The many-analysts study posits fixed research questions on a fixed dataset and invites teams of researchers to analyze the problem with whatever software they’re comfortable with. In Silberzahn et al. (2018), one question is to answer whether soccer referees are more likely to give red cards to dark-skin-toned player than to light-skin-toned players. The provided dataset contains two raters’ rating to the picture of players, the number of redcard received for each player/referee dyade out of the number of games, and a collection of player, referee, and game characteristics: player birthday, height, weight, player position, league country, number of victories, ties, and defeats, and number of yellow and red cards received. Most groups take a modelling approach to estimate the effect of skin rating on the red card issued with varied distribution assumptions (linear, logistic, and poisson) and covariate choices as fixed and random effects. The study is comprised of an initial analysis conducted separately by each team, followed by a round-robin peer evaluation round, and then each group presents their final analysis after incorporating the feedback from the discussion and presents the results in a way they would in a published article with formal Method section. All the materials related to the study is publicly available on the Open Science Framework (OSF).

From the report presented by each team, we can use LLM to convert the decisions into the schema designed and generate the corresponding coding script. From the write-up reports, we extract the sentences relevant to the decisions made in the final analysis by the team. This step is needed because the original skin rating is 1-5 but later changed to 0-1 and also many teams report their initial analysis and how their final analysis modify on top of the initial analysis. We do this to avoid confusion on reading comprehension with LLM. For general methodology write-up, this step is not necessarily needed [TODO: write it better].

We send the text description of the extractetd decisions for LLM to generate the schema and the code script for each analysis. The code script is run by a separate LLM to validate for potential syntax errors. We manually in-place replace the glm() command with fixest::feglm() (Bergé et al. 2026) for generalized linear model and the lme4::glmer() (Bates et al. 2015) function with glmmTMB::glmmTMB() (Brooks et al. 2017) for generalized mix-effect model to speed up the evaluation of eaach script. These two functions are in-place replacements of the classic functions for estimating the relevant model with implementation with multi-threading in C++ (Bergé et al. 2026) and with Template Model Builder (TMB) (McGillycuddy et al. 2025) for better performance. This replacement should not affect the estimation of the effect size. All the LLM-related simulations are conducted with claude-opus-4.5.

In the validation phase, all team scripts were successfully executed. Notably, 10% of the scripts (n = 2) yielded successful results without requiring any automated syntax corrections by the validator, whereas the vast majority (90%) reached completion after two or three iterations. The most frequent correction involved resolving broken and overflow syntax in comments.

Figure 2 shows the agreement of the estimated effect size, in odd ratio, from our experiments (simulated) and the published effect size in Silberzahn et al. (2018) (published). For most teams, the simulation successfully recovers the odd ratio reported by each analyst team, larger variations are seen in the following teams: Team 1, 9, 15, 21, 23, and 27. Here we listed the reasons for these discrepencies upon investigation:

  • Team 27: the diffference comes from the ambiguity of the method description, the final approach sections says In addition to the independent variables specified in the initial approach (skin-tone rating, goals scored, games played, yellow cards, and mean explicit and implicit bias) a variable for player position was included, as well as a variable for the league of the player. The author is intended to include the interaction effect of rating and position/ league country as other variables in the initial approach, but the LLM interprets it as only include the main effects. This error can be easily caught by comparing the reproducible script provided by the author.
  • Team 9: the authors mistake player country for referee country in the text description, but their parameter estimation table suggests they are using player country (countryCode - Germany: France) instead.
  • Team 23 and 1: the discrepency comes from the LLM fails to properly reshape the data from a player-referee dyad per observation to per game observation. The schema properly identifies this step but the generated code doesn’t execute this step properly and create a silent error with the validator.
  • Team 15: the discrpency comes from the default setting for estimating factor variable in R (our similuation) and SPSS (original script). In SPSS, the factor variables are estimated with effect coding, where the coefficients are compared to the grand mean, rather than to the reference group (dummy coding) in R. After changing the contrast options, we obtain the reported odd ratio.

4.1 Exploring alternatives

To demonstrate the functionality for specifying alternatives in Section 3.2, we use Group 5 from the football study above as an example. Group 5 uses a binomial generalized linear mixed model (GLMM) to estimate the effect of skin tone rating on the number of red cards received using a logit link function:

\[\begin{align*} \textbf{Model 1 (gm1):} \quad \text{logit}(p_{ijk}) &= \beta_0 + \beta_1 X_{ijk} + u_{j} + v_{k} \\ u_{j} &\sim N(0, \sigma^2_{\text{player}}), \quad v_{k} \sim N(0, \sigma^2_{\text{ref}}) \\[1.5em] \textbf{Model 2 (gm2):} \quad \text{logit}(p_{ijk}) &= \beta_0 + \beta_1 X_{ijk} + u_{j} + v_{0k} + v_{1k} X_{ijk} \\ u_{j} &\sim N(0, \sigma^2_{\text{player}}), \quad \mathbf{v}_{k} \sim N\left(\mathbf{0}, \mathbf{\Sigma}_{\text{ref}}\right) \\[1.5em] \textbf{Model 3 (gm3):} \quad \text{logit}(p_{ijkm}) &= \beta_0 + \beta_1 X_{ijkm} + u_{j} + v_{k} + w_{0m} + w_{1m} X_{ijkm} \\ u_{j} &\sim N(0, \sigma^2_{\text{player}}), \quad v_{k} \sim N(0, \sigma^2_{\text{ref}}), \quad \mathbf{w}_{m} \sim N\left(\mathbf{0}, \mathbf{\Sigma}_{\text{country}}\right) \end{align*}\]

where \(p\) denotes the probability of a player receiving a red card, and \(X\) represents the player’s skin tone rating. The subscripts \(i, j, k,\) and \(m\) index the individual observation, player, referee, and the referee’s home country, respectively. The parameter \(\beta_0\) represents the global baseline log-odds of receiving a red card, and \(\beta_1\) estimates the fixed effect of a player’s skin tone. The random structures account for multi-level variation across groupings with varying intercepts and/or slopes: (1) scalar random intercepts (\(\sigma^2\)) capture baseline shifts for players across all specifications (\(u_j \sim N(0, \sigma^2_{\text{player}})\)) and for individual referees in Models 1 and 3 (\(v_k \sim N(0, \sigma^2_{\text{ref}})\)); and (2) variance-covariance matrices (\(\mathbf{\Sigma}\)) accommodate random slopes, allowing the effect of skin tone to vary across individual referees in Model 2 (\(\mathbf{v}_{k} \sim N\left(\mathbf{0}, \mathbf{\Sigma}_{\text{ref}}\right)\)) and across referee countries in Model 3 (\(\mathbf{w}_{m} \sim N\left(\mathbf{0}, \mathbf{\Sigma}_{\text{country}}\right)\)).

5 Discussion

During the many-analysts football study, we document a set of observations regarding the performance of LLMs in parsing schemas, generating code, and performing validation. We find that LLMs requires a fairly precise specification in order to generate the code correctly for the intended random effect structure. For an educated statistician, the phrase “a random effect of referee number across average rating” would typically imply both a random intercept and a random slope. However, we observe that LLMs interpret this speicification literally as a random slope only. This suggests the gap between the latest models and human analysts in specialized statistical knowledge. Across the validation process, the LLM agent successfully corrects a range of implementation issues, including errors caused by overflowing comments and other syntax issues. However, we also observe challenges in data reshaping tasks when the transformation requires changes in the unit of analysis. In the study, some teams decide to transform the data from the original aggregated player-referee dyad-level format to game-level format. This transformation requires disaggregating aggregated outcome counts (win, loss, draw) into individual game records, changing the unit of analysis from dyads to matches. We also observe some difficulties in parsing birth dates. Since the LLM does not have access to the underlying raw data, due to privacy constraint, it must rely on trial and error when inferring the correct date formats (“DD-MM-YYYY.”). This suggests that certain types of data analysis tasks may not be fully automatable in settings where the model cannot directly inspect the data, even if the data is theoretically available for computation.

=== YOUR TASK ===

Extract a chronological list of methodological decisions (nodes) AND

simultaneously.

=== RULES ===

1. THEORY EXTRACTION: For each node, extract:

- 'id': A unique snake_case identifier.

- 'fork': MUST be framed as an open methodological goal that invites

- 'path': A 'path' is strictly a POSITIVE methodological decision
that has potential theoretical alternatives, chosen to resolve the
'fork'.

- 'rationale': WHY that decision (the path) was made, extracted from
the text.

2. DATA MAPPING: Assign 'inputs' (EXACT column names from the dataset
